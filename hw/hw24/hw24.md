# Практическое задание: Доработка API пользователей

## 1. Модернизация структуры данных
Необходимо обновить существующую модель `User`. При работе со структурами в Go важно учитывать, как данные будут сериализоваться (например, в JSON для микросервисов) и отображаться в логах для обеспечения их читаемости.

**Текущая структура:**
```go
type User struct {
    ID   int
    Name string
    Age  int
}
```

**Новая структура:**
```go
type User struct {
    ID       int    `json:"id"`
    Name     string `json:"name"`
    Age      int    `json:"age"`
    Password string `json:"password"`
    IsActive bool   `json:"is_active"`
}
```
> **Важно:** При создании нового пользователя поле `IsActive` должно автоматически получать значение `true`.

---

## 2. Авторизация пользователя (Login)
Реализуйте новый endpoint для проверки учетных данных. Рекомендуется логировать попытки входа, используя структурированный подход (например, через библиотеку `slog`), чтобы фиксировать как намерения, так и результаты выполнения.

*   **Метод:** `POST /login`
*   **Тело запроса:**
```json
{
    "name": "Alex",
    "password": "123456"
}
```

### Требования к реализации:
*   **Валидация:** Имя и пароль не должны быть пустыми. Ошибки валидации следует фиксировать в логах для мониторинга подозрительной активности.
*   **Проверка:** Система должна убедиться, что пользователь существует и его пароль совпадает с сохраненным.
*   **Ответы:**
    *   При успехе: Сообщение об успешном входе.
    *   При неудаче: Ошибка `401 Unauthorized`.

---

## 3. Мягкое удаление (Soft Delete)
Вместо физического удаления данных из хранилища необходимо внедрить логику деактивации. Это критически важно для сохранения истории и последующего аудита через логи.

*   **Метод:** `DELETE /users/{id}`

### Особенности логики:
*   **Действие:** Установите поле `IsActive = false` для указанного ID.
*   **Обработка ошибок:** Если пользователь уже имеет статус `IsActive == false`, верните ошибку.
*   **Traceability:** При выполнении операции логируйте уникальный идентификатор пользователя (ID), чтобы запись в логе была однозначной и легко находилась через `grep` или системы сбора логов.

---

## 4. Получение списков пользователей
Измените логику работы существующих endpoint-ов и добавьте новый для управления отображением активных и удаленных записей.

### Фильтрация активных пользователей:
*   **Метод:** `GET /users`
*   **Поведение:** Должен возвращать только тех пользователей, у которых `IsActive == true`.

### Получение полного архива:
*   **Метод:** `GET /users/all`
*   **Поведение:** Возвращает всех пользователей из базы данных, независимо от их статуса активности.

---

### Рекомендации (из источников):
*   **Логирование:** Для отслеживания цепочки вызовов в этом задании полезно использовать уровни логирования (INFO для успешных операций, WARN или ERROR для ошибок авторизации).
*   **Чистота кода:** Следуйте принципу DRY — логику проверки статуса пользователя лучше реализовать в самой функции обработки данных, чтобы не дублировать проверки в разных частях системы.
*   **JSON:** Поскольку API работает с пользователями, используйте JSON-формат для ответов, что является стандартом для современных микросервисов.
